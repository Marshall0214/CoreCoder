# 基础 Agent 反馈闭环修复方案

状态（2026-11-09）：前三阶段沙箱、动作循环与上下文/Schema 接口验收完成；第四阶段[五项本地真实验收](feedback-pilot-20261109.md)已完成，独立通过 1/5、基础设施错误 0，125 次调用/692,438 Token 与 Langfuse 回读一致。四项失败的反馈均未尝试编辑；读取坐标与动作空转是下一研究重点。服务端输入完整性仍为未核验，历史分数不改。依据：[50 项只读复盘](harness2-analysis-20261107.md)。

## 范围与协议

保留现有服务、评测器、Langfuse、补丁唯一锚点校验和 Docker 权限边界。新增可选 v2 入口、单独协议名和源码哈希；旧实现与成绩以冻结归档为准，不覆盖或回填。沙箱与反馈动作循环完成录制验收；新上下文/Schema 开关另立协议，三次本地调用只检查格式兼容。真实 Issue 与 Harness² 接入仍为后续工作，不产生修复率提升结论。

| --- | --- |
| 模型 | 已安装的 Ollama `qwen3.5:27b`，thinking=false；不使用 DeepSeek 或其他付费 API |

20 次模型请求与旧入口“20 次只能返回补丁的请求”拥有不同动作空间，因此 v2 是新协议，不作为单纯增加/减少轮数的消融。探索阶段仍单独计数，不能把两阶段总调用说成最多 20 次。

## 第一阶段：修复沙箱测试入口，零模型调用

问题：本轮 35 次反馈补丁应用后全部出现 `/runner.py` I/O 错误，原始对照也存在同类错误。先复现症状，不预设具体文件共享根因。

工作：

1. 从保存的 Toolz、itsdangerous、Click 补丁创建新的隔离诊断目录，保留原候选、原始响应、测试和日志不动；覆盖初始验证与反馈轮次深层目录两种路径。
2. 记录容器创建、启动、执行、结果读取各阶段；核对可信 runner、公开检查、候选源码的可读性、大小和哈希，区分入口 I/O 与被测代码失败。
3. 优先验证通过 `docker exec -i` 将可信 runner 经 stdin 交给隔离 Python，减少对临时单文件 bind mount 的依赖；这是待验证方案，不宣称已经找到根因。保持网络关闭、非 root、只读根文件系统、只读源码/测试、CPU/内存/PID/输出限制。
4. 将结果明确区分为测试通过、测试断言失败、runner 启动失败、结果缺失/损坏、超时、OOM、取消；保存原始退出码和 stderr，不只留下笼统的 `sandbox_invalid_result`。
5. v2 可对明确的测试启动基础设施失败做一次原输入、原候选的零模型重试；记录两个 attempt。测试断言失败不靠同样重试冒充修复。仍失败则以基础设施失败结束，保留待验补丁，不向模型发送虚假的测试失败信息。

验收：保存的 35 份 applied 后制品均获得可解释的实际执行结果；测试本身失败可以接受，入口 I/O 或丢失结果不能接受。正常、断言失败、超时、损坏结果和取消均有针对性覆盖；只清理本任务容器，不触碰其他服务。不得将保存补丁回放成功算作新的模型修复成果。

主要涉及：`sandbox/runner.py`、`repairflow/checks.py`、`repairflow/patch_validator.py`；相关验证扩展到现有 sandbox 单测与真实 Docker 测试。

## 第二阶段：让反馈阶段能重新获取证据

新增 v2 动作循环，复用已有搜索、文件读取、符号读取、唯一锚点编辑能力，所有读取都面向当前候选工作区。

```text
初始候选 → 公开检查
               ├─ 通过 → 冻结交付候选 → 任务结束后独立评分
               ├─ 环境故障 → 原候选有限重试 → 继续验证或记录基础设施失败
               └─ 代码/补丁问题 → 模型选择搜索、读取、编辑或结束
                                     ├─ 搜索/读取 → 返回证据 → 下一次模型请求
                                     ├─ 补丁被拒 → 返回具体错误 → 可重新读取
                                     └─ 补丁应用 → 自动公开检查 → 返回可判定结果
```

实现要求：

- 每次模型响应只提出一个明确动作，统一返回结构；执行器校验后执行，不让模型直接操作宿主机。
- 补丁之后自动触发公开检查，模型不需要另花一次请求申请测试；测试次数独立记录。
- 读到第一个完整符号不代表上下文已经足够；v2 允许继续查关联调用、协议方法或测试暴露的符号。优先打通反馈回路，初始探索复用工具与状态，不一次性重写整个项目。
- 读取收据带路径、符号、范围、文件哈希、工作区版本和完整性标记。编辑后使该文件旧收据失效；找不到锚点时允许回源读取，不进行无证据模糊覆盖。
- 编辑采用事务式应用：校验失败不污染工作区。保留任务基线、最新候选、最近公开通过候选及各次补丁；公开保持性回归时保存失败制品并恢复修改前快照，明确告诉模型已回滚到哪个版本。不得重置用户原始仓库。
- 环境故障下保留未验候选和最后已验候选，禁止把前者标为通过；取消终止所属模型等待、进程与容器，不启动新的修正。
- 达到请求/时间边界或模型主动结束时交付明确的未解决/待验证状态，不把自然语言“修好了”当作验收。

验收：用录制响应驱动真实工具和 Docker，完整演示“读源码→应用逻辑错误补丁→测试实际失败→根据公开报错读关联符号→再次编辑→公开通过”；另覆盖失效收据、锚点失败、回归回滚、取消、环境故障和第 20 次请求边界。该阶段无需真实模型。

已完成（2026-11-09）：真实 Docker 3 项通过，用时 30.07 秒；完整回放 5 次请求、3 次读取、2 次补丁、3 次公开验证，`Reproduce/Preserve` 按实际顺序为失败/失败→失败/通过→通过/通过。另通过响应后取消、运行中取消两项容器用例；独立 CLI 返回 `ready_for_review`、退出码 0。38 项离线结果沿用源码哈希未变的 11 月 8 日记录，覆盖事务、回滚、边界等其余机制；这些覆盖不全部等同于真实容器测试。11 月 8 日两次环境失败保留，新验收证据见 `.tmp/feedback-v2-20261109/acceptance-summary.json`。

主要涉及：`repairflow/feedback_repair.py` 或新增独立 v2 模块、`repairflow/issue_tools.py`、`evals/repository_checkpoint.py` 的可选衔接入口。现有其他修复入口默认行为不随之全部改写。

## 第三阶段：修正上下文和输出合同

接口验收已完成（2026-11-09）：显式 `--context-contract` 启用固定动作 Schema 和整段收据选择；150 项离线测试、3 项原有 Docker 回归、新合同 CLI 回放通过。Ollama 无思考三次短请求均生成合规指定动作，输入/输出共 3,413 原生 Token。估算目标不是累计截止，保护内容超目标时保留全文并标记；服务端截断状态仍为未核验。详见[实施与证据](feedback-context-contract-20261109.md)。下述真实任务完整性要求随第四阶段验证，不把合成短请求替代真实修复。

上下文按 Issue、动作 schema、最新错误、当前目标完整符号、必要依赖、补丁与检查摘要组织。allowed 文件列表只定义权限，不再代表每次必须发送全部文件。原始正文和历史轨迹继续保存在本地，模型可按需读取当前版本。

单次上下文采用可配置工作目标，例如约 8K～16K Token 的估算量；这是上下文组织目标，不是累计消耗上限。估算不当作原生 tokenizer 事实：保存实际请求、原生输入用量、上下文配置、选入/省略片段及服务器相关警告。超长符号明确分页和完整性，不能截断后仍标完整；关键约束、错误与编辑原文不静默删除。若当前有效容量不足，换成更小的可读证据包，不原样重发整库。

输出从泛化的 JSON 模式升级为动作 JSON Schema：为读取、搜索、补丁、结束提供固定字段和允许值；本地 Ollama 的 `format` 可以接收 schema，但具体 schema 与当前安装版本/模型的兼容性须用少量受控请求验收。生成约束后仍由执行器检查路径权限、字段、版本、唯一锚点与语法，不能保证代码语义正确。[Ollama 官方结构化输出说明](https://docs.ollama.com/capabilities/structured-outputs)

失败反馈直接说明错误字段、真实匹配次数和下一步可执行动作；不自动猜测字段映射、不把模型输出的 Diff 静默转换为另一种补丁。格式不合规同样消耗一次请求并保留原始响应。

验收：录制响应先覆盖 schema 各分支和恶意/畸形字段，再用本地短请求核验 schema、thinking=false 和 usage；代表任务的修复请求中无已确认的服务端输入截断，且读取收据与实际提交原文一致。若无法证明请求完整性，标为上下文异常，不把结果归为模型不会修复。

主要涉及：`repairflow/issue_providers.py`、`evals/local50_unmetered.py` 的可选 schema 接口、v2 上下文构建器与反馈模块。不能全局改动旧协议的请求格式后继续沿用旧分数。

## 第四阶段：固定五项本地机制验收

已完成（2026-11-09）：五项全部准入并独立评分，公开与独立均 1/5，Controls 全通过；Toolz 完成真实失败后再定位与修正。反馈 86 个响应均符合 Schema，但四项失败均 0 次补丁尝试。两阶段共 125 次调用、692,438 原生 Token，未知用量 0；10 条推理 Trace 与 5 份评分回读一致。运行后修正 `truncated=0` 日志误报，原记录与成绩保留，未重跑模型。详见[结果与归因](feedback-pilot-20261109.md)。以下为冻结验收要求，不等于已证明修复提升或服务端输入完整。

先完成前述零模型回放，再固定下列开发案例、当前源码/公开检查/独立检查哈希、模型 digest 和协议。每项先跑一次基础 Agent，不运行 Harness²，不选择性删除失败；额外诊断运行单独登记，不替换首次结果。

| 任务 | 主要验证内容 |
| --- | --- |
| toolz-join-unmatched | 小范围候选、公开验证与独立评分的端到端正常链路 |
| itsdangerous-none-salt | 补丁应用后，验证能真正启动，错误默认值有反馈而不是入口 I/O |
| boltons-split-zero | 长源码、补丁 schema 和精确锚点，避免 20 次猜测不落盘 |
| click-style-color-validation | 多文件上下文，按需读取而非整库发送 |
| more-negative-range-slice | 较复杂语义、长请求与模型失败/超时能被正确区分 |

Langfuse 与本地记录统一 experiment/task/protocol/attempt 标识；动作、应用、检查、回滚分别留痕。补充按逐调用聚合已知用量，任何缺失保持 null，同时报告已知下界；避免再次只累计用量完整任务。

每项报告：独立通过与否、公开结果、请求/读取/编辑/测试次数、拒绝原因、环境异常、回滚、耗时、原生 Token 及未知调用数。五项是已知开发案例，不作未见任务修复率声明。

进入下一阶段的标准：入口和结果可靠；能证明反馈后重新读取与再修改；至少一项真实模型执行完成“公开失败→编辑→重新公开验证”的链路；正常/失败/超时均有准确记录。无需五项全部修好，也不预先承诺成功率。若仍主要因接口或环境失败，则修这一层并单独记录复验，不扩大批次。

交付：独立 v2 入口、回放和集成验证、五项逐任务报告、Langfuse 可浏览轨迹，以及一条从 Issue 到 Diff/公开测试/独立结果的演示流程。服务层如需接入 v2，先做录制响应的一项 API 冒烟，避免 CLI 和服务宣称不同完成状态。

## 第五阶段：决定架构和模型，之后才验证 Harness²

只有上述机制验收通过后，再从一个问题出发选择下一次对照，不同时比较模型、框架和优化器：

- 若主因是检索/编辑控制流限制，固定本地 Qwen 与评分，使用现有 `evals/mini_swe_adapter.py` 接入路径做小样本对照，核对其任务环境和权限语义；保留服务、评测、Langfuse，不预先决定整套迁移。[mini-SWE-agent 官方循环](https://mini-swe-agent.com/latest/reference/agents/default/)
- 若执行健康但语义修复仍明显不足，再考虑少量同任务、同协议的强模型参照；付费 API 不是本计划当前执行项，不读取或使用 DeepSeek Key。
- 若要继续证明 Harness² 收益，两组必须使用同一修复后的基础循环、公开反馈、模型和独立评分，计算量差异单列。共享沙箱/反馈实现已变化，旧 24/50 不能继续作为新协议的同期基线。

下一轮全量不自动启动。先冻结新协议并建立健康的基础组，再决定 50 项两组对照或等计算预算对照；旧 24/50、27/50、25/50 全部保留为历史结果。公开检查的覆盖增强另立版本，不能把已知独立失败答案混入原协议后声称原实验提升。
