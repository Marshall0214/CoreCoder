# Click 候选补丁兼容性复核（2026-10-29）

**结论：候选补丁需要继续修改。**它仍通过原来的四项公开检查，但在六项新增样式保持诊断中失败四项；同一原始版本六项全部通过。原报告的“公开检查通过、待审查”记录保留，本次审查不认可其作为最终修复交付。

## 这次检查了什么

上一轮模型在“提供任意新样式参数”时清空输入中的 ANSI 序列。这能让显式蓝色覆盖输入中的红色，但也可能删除与本次修改无关的背景色、前景色和其他样式。

先阅读固定 Click 8.1.8 源码与已有测试，再编写诊断：

- `style` 的参数说明分别描述前景色、背景色和加粗；`reset=False` 的说明明确提到组合样式。
- 上游 `tests/test_utils.py::test_styling` 检查颜色、加粗及不追加 reset 的输出，但未直接覆盖本次四种组合回归。
- 本次新增用例由项目编写，并在看到补丁后设计；预期依据参数职责、文档和原始行为，不冒称上游测试或独立隐藏评分。源码依据和许可证保存在[证据包](compact_candidate_review_20261029/NOTICE.md)。

原始源码与候选源码分别在同一个固定 Docker 镜像中执行原四项检查和新六项诊断。候选差异先与冻结补丁核对，只有 `src/click/termui.py` 变化；测试代码和执行器不交给模型，也不在宿主机导入候选代码。

## 实际结果

| 检查 | 原始版本 | 候选版本 |
| --- | --- | --- |
| 原目标：显式蓝色覆盖原红色 | 0/1 | 1/1 |
| 原正常行为检查 | 3/3 | 3/3 |
| 新样式保持诊断 | 6/6 | 2/6 |

六项诊断逐项结果：

| 场景 | 原始版本 | 候选版本 |
| --- | --- | --- |
| 添加加粗时保留已有红色 | 通过 | 失败，红色丢失 |
| 设置蓝色前景时保留已有黄色背景 | 通过 | 失败，背景丢失 |
| 设置蓝色背景时保留已有红色前景 | 通过 | 失败，前景丢失 |
| 嵌套 `reset=False` 样式时组合颜色与加粗 | 通过 | 失败，内层颜色丢失 |
| 普通文字设置颜色且 `reset=False` | 通过 | 通过 |
| 普通文字同时设置前景、背景与加粗 | 通过 | 通过 |

例如，给红色文字增加加粗，应该得到“红色且加粗”；候选先删掉红色序列，最终只剩加粗。错误来自修改范围过大，不是 Docker 故障、补丁应用失败或输出截断。

本次共执行六组容器检查、20 次测试用例执行。原始版本目标失败及候选四项回归均为实际断言失败；没有超时、测试错误或跳过。诊断状态解析器及已有观察精简测试 **24 passed**，Ruff 通过。该解析器只支持本次基本 SGR 状态，不声称覆盖完整终端、256 色或 RGB；遇到不支持的 SGR 代码会拒绝解释。

## 对系统的含义

这次区分了两个问题：

1. **历史观察精简减少请求重复。**上一轮固定历史状态离线估算减少 40.55%；实际单次轨迹 Token 由 53,252 降至 24,704。此次审查不推翻这些成本记录，也不把它们当成修复正确性证据。
2. **公开检查覆盖不足。**候选满足原检查，却破坏已有行为。新增诊断提供了具体反例，审查结论为 `needs_revision`；通过公开检查仍需审查。

本次没有修改候选，没有调用本地或云模型，没有启动第二轮方法试验；累计真实任务运行仍为 **1/6**、方法试验仍为 **1/2**。原四项检查、原候选报告、冻结证据包和历史 47/50 均不修改。这里也没有给运行系统新增自动审批阻断规则，`needs_revision` 是单独的审查产物。

后续若继续改补丁，约束应是“只覆盖显式指定的样式维度，保留其他样式和可见文字”，而非“清除所有 ANSI”。先用这些反例及原目标验证候选，再考虑扩展不同颜色编码、reset 与控制序列的覆盖；该方案尚未实现或证明。新诊断一旦用于反馈便属于开发测试，不能再当作未见的独立评分。
