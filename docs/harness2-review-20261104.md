## 2. iteritems 是怎样进入补丁的

原始 `toolz/itertoolz.py` 第 918 行已有 `for key, matches in iteritems(d):`。这是 Left/Full Join 共用的未匹配左行输出循环；文件没有定义或导入 `iteritems`。因此不能把这个符号全归因于模型凭空发明。

领域和合成执行均在第 4 步通过 `read_symbol(join)` 得到 **813–921 行、3857 字符、complete_symbol=true**；第 5 步候选请求也实际包含该函数，里面包含 `iteritems`。当前工具确实返回了完整函数，不能把这两个补丁失败简单解释为函数被截断。

模型接着在 Left Join 分支内新增同样的循环，同时保留原来的公共循环：

```text
Left Join 分支：新增循环，调用 iteritems(d)
分支结束之后：原公共循环仍在，也调用 iteritems(d)
```

这带来两个问题：未修复原有未定义符号；即便只修好名称，也会对未匹配左行输出两次。领域/合成补丁完全相同，后者没有纠正前者。

## 3. 组件开放决策

按最新要求，**仅新增 Context Builder 的声明式配置层**，作为可测试接口，默认不开启新模式。该决定是扩大研究接口的工程选择，不是已证明 Context Builder 是本次补丁失败的主因。暂不开放 Retrieval、Patch Validator 策略、Skills、Memory、工具实现、Runtime 或评分器。

显式使用 `--context-policy` 时允许第三份 `context_policy.json`：

```json
{
  "version": 1,
  "deduplicate_reads": false,
  "complete_symbols_first": false,
  "read_index": false
}
```

- 去重只合并完全相同的源码片段、重复成功读取的观察；不同路径、版本、偏移、符号的片段保留。错误、搜索、补丁及保护停止不去重，完整原始 Trace 始终保留。
- 完整符号优先只调整已有片段的次序，不增加文件读取。读取索引只由当前有效片段生成，不保存跨任务记忆，不假装建立调用图。
- 默认三个开关全关，保持原始请求对象和 JSON 字节；不删除 Issue、剩余步骤、权限契约或完整函数。不设新的 Token/上下文上限，不改变旧 ledger 的限制。
- 未声明字段、重复 JSON 键、非布尔开关、检索配置、脚本、模型及预算字段均拒绝。独立评分仍在 Agent 停止之后。
- 每次实际送入模型包装层的请求保留在 `context-requests/call-NNN.json`，带 experiment_id、task_id、harness_variant 和配置；这是策略与指导处理后的请求。旧 step-NNN-messages.json 是注入指导之前的记录，不应误称为原始网络请求。

源码 [harness2_context.py](../integrations/harness2_context.py)，接口接入 [harness2.py](../integrations/harness2.py)，边界检查 [test_harness2_context.py](../tests/test_harness2_context.py)。不带新开关的入口仍只允许原两份指导文件。
