## 已确认的问题

最新配对记录中，none-salt 的第一轮删除了 `Serializer.make_signer` 和 `Serializer.iter_unsigners` 的 `salt is None → self.salt` 回退；第二轮又为构造函数补入固定默认值，最终仍未通过目标与控制测试。

第二轮已经包含完整公开测试、当前已编辑函数和源码契约事实。因此不能归因为“没有提供测试”或“完全没有看到修改位置”。目前的反馈提示没有单独展示第一轮补丁的前后差异；模型看得到当前候选，但缺少紧凑的修改历史。是否因此难以撤销错误修改，是待验证假设，不能当作已证实原因。

## 下一项实现

新增可选的补丁差异反馈：从任务起始快照和实际提交的候选计算修改差异，反馈同时提供失败观察、当前函数原文与修改前后差异，让模型可以修正或撤销自己的第一轮修改。

- 差异只来自模型实际修改的源码，不读取参考修复、私有评分测试或隐藏答案。
- 旧版本差异只用于解释历史；编辑锚点仍须匹配当前版本，避免用旧代码误改。
- 不增加模型请求：仍最多两次，共享 15,000 Token；首轮提示保持一致。
- 差异纳入原有 6,000 字符证据预算，保留必需的当前已编辑函数，再减少低优先级片段；不能借添加历史偷偷扩大预算。
- 保留原策略和冻结报告，不直接替换默认 Agent 或服务。

## 验收与停止条件

先离线验证差异确实包含已删除逻辑、版本和哈希正确、预算内装填，以及旧锚点不会被当作当前编辑证据；这些检查不需要模型调用。

随后在同模型、同预算下，对 none-salt 和已修复的 Click 任务做新配对验证，使用独立目标与控制测试。只有修复结果改善且没有回归，才扩大到已有六项任务复核；若只是增加上下文和 Token 而没有改善，不继续堆叠这一策略。

主要指标是独立修复通过数和控制测试回归数；能否恢复原有行为是诊断指标。源码保护、单测数量和更多报告均不能替代修复收益。
