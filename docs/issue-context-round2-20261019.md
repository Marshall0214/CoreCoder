## 本轮实现

新增 `repairflow/issue_context.py`，只作用于已准备 Issue 的修复入口：

1. 原检索判定为必选的目标函数优先保留。
2. 补充这些函数所在模块的真实导入，导入总量最多 1,200 字符。
3. 补充公开测试调用的同模块顶层辅助函数，再补目标函数的直接辅助函数。
4. 剩余位置使用原检索候选；总量仍最多 6,000 字符、5 段，记录舍弃原因。

AST 只用于静态解析，不执行仓库模块，不扩大允许读取和修改的文件范围。
行范围、原文和文件哈希继续交叉校验；相关函数的判断是静态近似，不是完整类型分析或调用图。
本例从 `style / secho / _interpret_color / progressbar / prompt` 重排为：
`style / secho / 模块导入 / unstyle / _interpret_color`。
目标片段保留原样，提供了现有 `strip_ansi` 的导入与使用线索。

另增加净变化诊断：一次已应用补丁修正后，若源码完全回到基线，保留原公开检查并报告 `no_progress`。
它不增加生成次数，也不放宽交付规则；本轮真实推理中的补丁均未应用，因此该诊断没有触发，另外由单元测试验证。

## 本轮为什么没有提升

两次回答都试图提供完整 `style()` 函数作为 `old`，其中包含未提供的函数声明和自行重建的文档；整段文本与实际代码不符。
逐字检查确认，两份 `old` 在原始文件中都出现 **0 次**。
执行器先在证据范围校验处返回 `Edit text was not supplied in local context`，没有把错误补丁应用到文件。

第一次拒绝后，错误信息和原始测试观察已经进入第二次请求，但模型仍生成了不真实的完整旧函数。
因此，补充导入信息没有解决本次出现的锚点复制问题；输入变短的同时，输出变长，总成本反而增加。
补丁没有实际运行，不能把“没有再出现 NameError”解释为成功修复了第一轮的符号问题。

锚点、范围和公开测试规则保持严格。原始源码与测试未改变，最终 diff 为空，本任务没有遗留容器。
