## 1. 外层完成，反馈闭环没有正常工作

“流程错误 0”仅指 50 项 PPC 的编排、交付和最终评分完成，**不能解释为内部工具、模型和验证都没有出错**。

| 本轮 200 次反馈入口的终态 | 次数 | 实际含义 |
| --- | ---: | --- |
| ready_for_review | 87 | 全部是初始候选已通过，修正请求数为 0 |
| feedback_round_limit | 46 | 每次 20 轮全被拒绝，合计 920 次、0 次应用 |
| validation_blocked | 36 | 35 次补丁应用后的执行入口 I/O 错误，另 1 次初始测试超时 |
| local_provider_failed | 30 | 模型请求失败，Token 用量未知 |
| task_timeout | 1 | 整次执行达到时间边界 |

35 次反馈补丁成功应用后，35 次公开 Reproduce 验证全部未能读取沙箱入口：

```text
python: can't open file '/runner.py': [Errno 5] Input/output error
```

返回码 2，stdout 为空，没有生成有效测试结果，最终记为 `sandbox_invalid_result`、`public_checks=null`。这发生在测试启动前，不是断言判定补丁错误。冻结实现把宿主机生成的脚本只读 bind mount 为 `/runner.py`，再通过 `docker exec` 运行；现有证据定位到入口文件读取失败，尚未证明具体是 Docker Desktop、WSL 文件共享还是文件生命周期问题。已检查示例宿主路径都不足 260 字符，不能直接归因为 Windows 路径长度。

**历史控制组也存在同样故障**：原始组 11 次 applied 后 11 次相同 I/O 中断；旧 Harness² 24 次 applied 后 24 次相同中断。它不是本轮新增，也不是 Harness² 独有问题。旧组采用相同实现使历史复用仍可追溯，但这些数字不代表健康反馈链路中的策略对照。

本轮没有一条“经过反馈修改后，新通过公开验证”的完成记录。后置独立评分仍然实际执行，25/50 是本批真实交付结果，不增加任何推测成功项。

## 2. 20 次请求多数没有形成有效编辑

1,181 次公开反馈请求中，**1,115 次（94.41%）被补丁校验拒绝且工作区哈希不变**：839 次 schema 错误、193 次锚点不存在、65 次语法错误、17 次无变化、1 次锚点不唯一；另有 35 次 applied、30 次 provider 失败、1 次超时后未应用。

例如 Click 的颜色校验任务，模型返回 `{action: generate_patch, patch: diff}`，下一次返回 `path/start_line/old_content`，执行器只接受 `{edits: [{file, old, new}]}`。这不能算 20 次实际补丁迭代。Boltons split-zero 的四次执行累计 80 次反馈全部拒绝，源码始终未改变。

反馈实现每次发送全部 allowed 文件；例如颜色校验的 agg1 首轮附带 32 份完整文件，源码正文 456,399 字符，请求正文约 493,397 字符。对应调用时间内，本机 Ollama 原日志明确记录：

```text
time=2026-11-06T14:06:20.299+08:00 ... msg="truncating input prompt" limit=32770 prompt=125361 keep=4 new=32770
```

服务端将该请求的输入从 125,361 Token 截到 32,770。反馈中 1,151 次有原生用量的调用，1,138 次输入恰为 32,770；批次时间窗内服务器共有 1,167 条截断警告，但这个服务器级计数不等于逐请求唯一归属。公开反馈在保存的请求正文后部，**究竟保留了哪些片段仍未知**；不能仅靠截断现象断定每次格式错误的唯一原因。

之前优化的是“策略编辑器如何读取执行证据”；这并没有修好“修复器如何接收公开反馈和源码”。三布尔 Context Builder 对唯一的整文件列表不能产生有效缩减。

## 3. 正确性缺口和选择器的边界

25 个最终失败交付中：11 个没有最终源码变化；12 个有非空补丁但 Target 未通过；2 个 Target、Controls 同时未通过。25 个失败交付的反馈终态分别为：14 个耗尽轮次、5 个 provider 失败、4 个验证阻塞、2 个公开 accepted。

公开 accepted 的 25 个交付中，23 个独立通过，2 个独立未通过：

- `click-flag-envvar` 的公开检查只验证关闭值不返回 `UPPER`，返回错误的 None 也能通过；独立检查要求准确结果。
- `click-prompt-suffix` 的公开检查只覆盖 `prompt()`，未覆盖 `confirm()`，补丁漏改后者。

固定交付规则依次选公开 accepted 的 `agg1 > base1 > inv1 > dom1`；全部未 accepted 时仍交付 agg1 失败产物供独立评分。实际 47 个 agg1、2 个 base1、1 个 dom1。它是公开收据准入和固定优先级，不是模型质量投票。

14 项四个候选最终完全相同；31 项交付哈希与 base1 相同。没有发现已知独立成功的候选被选择器丢弃，造成本轮失败的证据；未交付的不同补丁没有独立评分，正确性未知。唯一新增成功 `more-permutation-exception` 的 inv/dom/agg 在探索阶段已产生同一补丁，不能将收益归为合成或反馈独有贡献。

三项旧成功丢失也有具体机制：none-salt 首次修改后验证入口失败，交付补丁同时破坏默认语义；split-zero 80 次反馈未应用任何补丁；negative-range-slice 多个候选首轮反馈约 480 秒后请求失败，错误反向切片未被纠正。完整补丁与测试日志定位见归档 `selection-notes.md`、`failure-notes.md`。
