# CoreCoder：Agent 前沿技术调研与学习路线

调研日期：2026-11-06（Asia/Shanghai）。范围为与当前 Python Issue 修复项目直接相关的技术，采用论文、作者仓库和官方工程文章。这是定向初步调研，不是穷尽性文献综述；下文方案是建议，尚未运行新模型实验。

## 1. 建议的项目主线

把 CoreCoder 推进为“能根据公开执行证据调整修复策略、复用经过核验的经验，并用独立评测衡量收益与成本的 Coding Agent”。

近期优先级：**评测与失败归因 → 上下文和动作收敛 → 等预算策略对照 → 经验准入与迁移 → 自适应探索 → 模型训练**。

学习分成两个问题：

- 人如何学习 Agent：读清主循环、工具、上下文和验证边界，逐条跟踪真实失败，再读论文并做最小对照。
- Agent 如何学习：先调整输入和执行策略、积累可撤销的经验；数据和评测成熟后，再考虑更新模型权重。

## 2. 项目现状与可支持的判断

依据本地 README_CN.md、plan.md、最近的评测与审计文档，以及抽查的实现入口：

| 已有证据 | 可以说明什么 | 尚不能说明什么 |
| --- | --- | --- |
| 自有 Agent 历史本地轮次 21/50 | 指定历史协议下的结果 | 不能与其他轮次直接合并计算提升 |
| 旧版公开反馈对照：原始组 24/50、Harness² 27/50 | 同一已知任务池，净增 3 项；新增成功 4 项、丢失 1 项 | 总计算量不同，不能据此证明策略搜索优于同成本重复尝试 |
| 旧版累计耗时约 4.47 倍、6 项流程错误 | 成本与流程可靠性是实际问题 | Token 有未知值，不能报告精确 Token 成本倍数 |
| Toolz 新版完整 PPC 成功交付 | 编辑、执行、经验审查、交付与独立评分链路可以完成 | 四次探测最终补丁相同，均通过公开反馈修正；不能认定策略指导贡献了修复收益 |
| 新版 50 项评测运行中 | 已冻结协议并启动 | 调研时没有完整成绩，不预判新版分数 |

本轮只读查看了运行报告的状态字段，不干预正在进行的批次。研究文档单独新增，既有运行代码与计划保持原状态。

当前已有 Docker、公开反馈、独立评分、Langfuse、符号读取与 Harness² 接入。由此判断，下一步最有价值的问题是“什么证据能改变修复动作、每份额外计算带来多少成功、经验能否迁移”。

## 3. 应优先学习的技术

### A. 上下文工程与长任务执行：立即学习

研究问题：每次调用应该给模型哪些事实，什么时候读取更多材料，什么时候必须采取编辑或提交动作？

Anthropic 的上下文工程文章讨论有限上下文中的信息组织和按需检索；长任务文章介绍初始化、逐步推进及向下一会话交接状态。它们是工程经验，不能直接当作本地 Qwen 的实验结论。[上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)、[长任务 Harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

项目落点：

- `corecoder/context.py`：通用会话压缩。与下面的 Issue 修复上下文入口分开理解，不能假设改这里就改变所有修复流程。
- `repairflow/issue_context.py`：修复定位与上下文获取。
- `integrations/harness2_reader.py`：策略编辑器的证据索引、短材料和按需读取。
- `repairflow/feedback_repair.py`：公开反馈后的补丁修正。

建议最小实验：在固定失败案例上，只调整“当前补丁、准确符号、最近公开失败、已尝试动作”的呈现顺序，完整原文继续可按需读取。先测是否减少重复读取、是否更早生成有效补丁、是否遗漏必要证据，再测独立成功率。现有去重实验没有修复收益，不能把输入变短作为目标本身。

### B. Harness² 与 GEPA：立即学习，分别理解

Harness 是模型外的执行系统，包括提示、工具、上下文、记忆与控制流程。

- **Harness²**：2026-10-09 提交；任务内通过 Propose–Probe–Compose 对比执行并修订 Harness，还提取跨任务的改进经验；模型权重保持不变。论文明确承认额外执行与编辑成本。[论文](https://arxiv.org/abs/2610.14224)、[作者仓库](https://github.com/google-research/harness2)
- **GEPA**：2025-07 初稿、2026-02 修订；利用执行轨迹和文字反馈反思提示，用候选搜索与互补经验合成改进系统。其训练/开发反馈设置应与 Harness² 的任务内无真值设定区别对待。[论文](https://arxiv.org/abs/2507.19457)
- **近期扩展**：2026-10-27 的批量反思优化工作研究并行提出与评估 GEPA 候选。其报告来自数学与事实验证任务，不能直接外推至 Issue 修复；本地单模型服务也未必具备相同并行吞吐条件。[论文](https://arxiv.org/abs/2610.36774)

项目建议：继续理解已有 Harness²，先补“同等预算的普通重复尝试”对照。GEPA 适合后续在开发集优化通用指导，然后冻结指导到未见任务评测。避免一轮同时引入两种优化器，导致无法归因。

### C. ACE 与经验记忆：第二个重点

ACE 初稿发表于 2025-10，当前核对版本修订于 2026-03。其核心是生成、反思、整理相分工，以条目化增量更新积累策略，避免反复重写整份提示造成知识丢失。条目可以记录有益或有害的使用反馈。[论文](https://arxiv.org/abs/2510.04618)、[方法正文](https://arxiv.org/html/2510.04618v3)

建议先做小型 JSONL/SQLite 经验库，验证学习机制后再选择存储产品。每条经验至少包含：

```json
{
  "id": "experience-001",
  "scope": {"repository": "example", "source_revision": "pinned-revision"},
  "trigger": "公开证据中可以识别的触发条件",
  "action": "建议采取的检查或修复步骤",
  "evidence_refs": ["public-trace-id", "public-validation-receipt"],
  "validation_status": "candidate",
  "counterexamples": [],
  "supersedes": null,
  "revoked": false
}
```

这份结构是项目建议，不是 ACE 的原始 schema。经验应附适用范围与反例；公开检查通过只说明其公开验证状态，不等同于完整正确。避免保存“某个固定任务直接替换某行”的答案式记忆来声称泛化。独立评分及其日志不进入经验生成、检索或策略决策输入。

已有候选：

| 方案 | 主要解决的问题 | 本项目建议 |
| --- | --- | --- |
| JSONL/SQLite | 定义经验准入、来源和撤销的最小机制 | 第一版使用，便于审计与对照 |
| Mem0 | 提取、保存、按标识隔离和检索记忆 | 机制有效后再比较；默认提取会调用 LLM，需显式选本地方案 |
| OpenViking | 统一组织记忆、知识与技能的上下文数据库 | 当资源组织和检索成为明确瓶颈时再评估 |

产品定位与行为已核对 [Mem0 官方 add 文档](https://docs.mem0.ai/core-concepts/memory-operations/add) 和 [OpenViking 官方仓库](https://github.com/volcengine/OpenViking)。采用它们本身不构成 Agent 学会修复的证据。

### D. 自适应探索与 DREAM-RSI：机制成熟后研究

DREAM-RSI 改进的是探索预算分配策略；固定底层 Agent、任务和评估器，先形成探索树，再在保存的世界中回放比较策略。[作者仓库](https://github.com/google-research/dream-rsi)

项目可以先比较“固定重试”“固定 PPC”“基于公开执行状态触发 PPC”三种规则。触发条件只读取当时可见证据，例如定位失败、补丁无效或公开测试错误类型。历史独立分数不能作为在线触发输入。

边界：现有线性轨迹不一定包含新策略想探索的分支，离线回放不能凭空产生反事实执行结果；最后必须在新任务上真实执行。官方仓库也明确列出未包含论文中的 Harness 优化实验，因此复现范围需逐项确认。

### E. 多 Agent：理解适用条件，后置实现

优先考虑能够独立完成的定位调查和候选方案研究。对同一文件的强依赖修改，需先定义工作区、交付格式与冲突处理。Anthropic 的工程文章明确讨论额外成本及部分编码任务不易并行的问题。[官方经验](https://www.anthropic.com/research/multi-agent-research-system)

对当前项目，建议先让单 Agent 的“读取—修改—验证—提交”可靠收敛。以后比较多 Agent 时，总调用和执行成本必须包括协调者与所有工作者。

### F. Agent Lightning 与强化学习：后续训练方向

2026-08-18 的 Agent Lightning v1.0 研究让部署时 Harness 直接参与强化学习，交互循环由 Harness 管理、训练器获取模型请求与响应；论文给出编码 Agent 的训练流程。[论文](https://arxiv.org/abs/2608.17528)

当前先学习 rollout、轨迹质量、奖励设计、优势估计和 reward hacking。等到有足够多去重任务、可信反馈、固定留出集、干净轨迹和明确算力配置，再考虑小规模 SFT 或 RL。当前 50 项已知缺陷不足以独自支撑泛化训练结论，也没有核验本机具备训练 27B 的资源条件。

## 4. 推荐的四周学习与交付安排

以下按每天约 1–2 小时估算，作为学习节奏；模型实验数量和预算应在每轮协议中单独固定。

| 阶段 | 学习与工作 | 可检查的产物 |
| --- | --- | --- |
| 第 1 周：读懂当前系统 | 阅读 `corecoder/agent.py`、工具、`corecoder/context.py`；再读 Issue 修复入口、Validator 和真实轨迹；学习 Agent eval | 一张执行链说明；从旧案例建立 8–10 项失败诊断集，每项附证据与失败阶段 |
| 第 2 周：策略与上下文 | 精读 Harness² 方法、成本与失败章节；比较 GEPA；只选择一个上下文变量 | 冻结的小样本消融协议；测重复读取、首次有效编辑、公开验证、独立结果和全部成本 |
| 第 3 周：经验机制 | 阅读 ACE 方法；实现候选、核验、冲突、版本隔离与撤销 | 可追溯的小经验库；无记忆、随机无关记忆、相关记忆三个对照的设计与最小验证 |
| 第 4 周：迁移与演示 | 新任务冻结后评测；视资源做少量独立重复；学习 DREAM-RSI 的探索思想 | 开发/留出结果、成功新增与丢失、成本曲线；一条 Issue 到候选补丁与审查报告的演示 |

第 1 周建议阅读顺序：

1. 第 1–2 天：主循环、模型接口、工具契约，跟完一次任务的消息与工具响应。
2. 第 3 天：定位、符号读取、锚点编辑及重新读取恢复。
3. 第 4 天：公开反馈、Docker 验证和独立评分，画清信息边界。
4. 第 5 天：读旧版失败审计和新版 Toolz 轨迹，逐次解释模型为什么继续读取或提交。
5. 第 6 天：读 Harness² 的任务内/跨任务两层递归，和本地适配器逐项对照。
6. 第 7 天：完成失败分类与一个可证伪假设，例如“决策证据前置能减少无效读取且不损失修复成功”。

每篇论文固定回答：优化对象是什么、用了什么反馈、成本是什么、任务如何划分、相对什么基线、失败在哪里、在本项目如何最小验证。

## 5. 下一轮实验应如何设计

### 先分析正在运行的新版批次

批次结束后统一统计：完整 PPC 率、流程错误、公开通过、独立通过、新增成功、成功丢失、候选回退、编辑与执行调用、Token 已知覆盖率、耗时。用旧版作版本回归参考；历史对照复用不等于重新独立运行。

失败诊断建议至少分为：定位错误、证据不足或读取循环、补丁语义错误、锚点/格式错误、公开反馈无进展、候选交付错误、模型/环境故障。分类以实际轨迹为准，不能只看最终测试错误猜测原因。

### 然后进行等预算对照

| 组别 | 处理方式 | 要回答的问题 |
| --- | --- | --- |
| A | 原始指导下重复独立尝试，使用相同公开反馈与预定候选规则 | 单纯增加尝试能得到多少成功？ |
| B | Harness² 策略搜索，包含编辑与反思成本 | 策略优化是否胜过同预算重复尝试？ |
| C（后续单独一轮） | 固定执行方式，增加冻结的相关经验 | 收益是否来自经验迁移？ |

建议先做 A/B，再做记忆消融，避免变量混杂。预先选择统一的总请求预算或累计执行时间口径，把编辑器、执行器、反馈和失败全部计入；另一成本维度完整报告。若要匹配 Token，先保证完整用量可得，并单独制定新协议。既有实验不设 Token 截止，本调研不改变当前运行限制。

诊断集可以挑选历史失败，用于提出假设；用于最终报告的留出集应在调参前固定，尽量按仓库、时间或缺陷族隔离，并检查近重复。现有 50 项全部作为已知开发材料。留出期间冻结提示、记忆与选择规则，独立评分后不反复调参再声称仍是首次留出评测。

重点指标：最终独立成功率、过程错误率、成功新增/丢失、总调用、完整用量覆盖、累计耗时，以及相同预算下成功数。小样本和单轮只能给方向信号；重复次数与不确定性如实报告。评测方法可先读 [Demystifying evals for AI agents（2026-01-09）](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

## 6. 近期最小交付

1. 新版批次完成后的完整对照与失败分类。
2. 一套基于已知失败的诊断材料，以及独立冻结的新任务清单。
3. 一个上下文或策略变量的最小对照，解释是否值得继续。
4. 有证据、可撤销的经验准入原型。
5. 演示一次从 Issue、定位、候选修复、公开验证到审查报告的完整过程，并能打开相应 Trace。

这五项交付能同时推进工程展示与研究能力。新增框架应对应已观察到的瓶颈，并通过小实验决定是否保留。
