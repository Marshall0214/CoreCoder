## 两个失败点与证据

**合成编辑器没有形成决策。** 它先读取任务，再顺序读取 base1 和 dom1 的多页轨迹，然后读取 inv1 末页。20 次读取中有 17 个不同的文件/偏移/长度请求，最后 3 次重复了已读的 dom1 页面；没有读取候选指导文件或补丁，就耗尽会话请求数。

这不是原先的整包输入超过字符上限，也不是格式校验反复失败。按需接口成功提供了原文，但模型仍优先扫描长轨迹，没有利用已给出的候选终态、指导文件和补丁索引收敛到 KEEP_BASE 或具体合成方案。小文件持续保留也不能帮助尚未读取的材料。证据见归档 `run/experiment/editors/call-003/reader-report.json`、各步请求及读取结果。

**控制器交付路径的依赖边界不完整。** 官方核心已返回 `partial`，随后调用公开候选选择器时，Python 3.12 通过 `evals.runner → evals.runtime → corecoder.__init__ → corecoder.llm` 间接导入缺失的 `openai` 包，抛出 `ModuleNotFoundError`。这是本地控制器依赖故障，没有发生云端 API 调用；它掩盖了外层报告中的合成失败。3.12 的纯导入复现报错保存在 `run/recovery/controller-import-error.txt`。

本轮保留原始 `report.json` 和 `experiment/result.json`，没有安装依赖、改运行代码或重跑模型。独立的后置恢复脚本在既有 3.11 环境中执行同一预定公开规则，选取 base1，再运行 Docker 独立验收：**Target 1/1、Controls 1/1**。恢复新增模型调用 0，原始报告哈希不变；恢复交付不补齐缺失的 agg1/经验阶段。

## 指导是否真正生效

后置审计核对了：

1. 两份编辑器输出与对应修复 job 的 Harness 内容逐项一致，内容哈希与 Agent 报告一致。
2. 34 份探索阶段的有效模型请求中，指导位于实际发送的 System 消息，Context 配置与声明一致；三次反馈请求也携带同一指导。
3. 每次读取都对应本会话固定快照中的 ID、文件哈希、字符区间和原文；编辑器没有索引独立评分材料。
4. 修复从同一缺陷源码重新执行，没有候选复用；独立评分只在 PPC 终止、公开候选选择完成后运行。
5. 执行实现、原 14 份本地 Agent 基线文件、旧完整批次报告哈希不变。

这里验证的是指导传递和上下文组织接口。通用与领域组仍重复读取，最终与原始组依靠同样的一次反馈产生相同补丁；不能据此声称指导改善了任务推进或修复能力。
