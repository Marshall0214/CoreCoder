# 相关开源工作与本项目定位

检索日期：2026-10-06。以下依据作者维护的 GitHub README、官方文档和论文入口；未安装这些项目或复跑其公布结果。本文不将不同模型、预算或数据集的成功率与我们的七个开发任务比较。

| 工作 | 已解决的相关问题 | 当前最值得借鉴的内容 | 接入判断 |
| --- | --- | --- | --- |
| [SWE-agent](https://github.com/SWE-agent/SWE-agent) / [ACI 说明](https://github.com/SWE-agent/SWE-agent/blob/main/docs/background/aci.md) | 面向模型的搜索、文件查看和编辑接口；研究接口设计对修复行为的影响 | 有界阅读、搜索结果压缩、编辑检查；为工具接口消融提供先例 | 当前先借鉴实验设计；搬入工具后需统一响应、范围权限与预算计量 |
| [Agentless](https://github.com/OpenAutoCoder/Agentless) | 文件→类/函数→编辑位置的分层定位，随后生成补丁和验证 | 将定位与修复分开；提取代码结构；独立记录各阶段成本 | MIT；适合作为未来结构定位对照，需要适配我们的任务、模型和独立验证器 |
| [LocAgent](https://github.com/gersteinlab/LocAgent) | 将代码结构与依赖表示为异构图，以搜索和多跳导航定位代码 | 图索引、实体级定位、BM25 与图导航；官方 README 亦提供 CodeNib 集成入口 | Apache-2.0；图构建及索引适配成本高于当前 AST 阅读工具，待单文件阅读问题验证后再做独立策略 |
| [aider repository map](https://aider.chat/docs/repomap.html) | 用符号定义、引用关系与图排序，在 Token 预算内生成仓库地图 | 基于相关性选择结构上下文，避免把所有源码放入提示 | 借鉴选择方法；不能与完整函数阅读混在同一干预中，否则无法解释收益来源 |
| [mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent) | 简单控制流、仅 bash、线性历史与可替换运行环境 | 作为“复杂专用工具是否必要”的反向基线；降低框架复杂度 | MIT；外部对照需 Linux/容器与相同任务评分，bash 预算和工具能力必须另列 |

SWE-agent 当前 README 明确将主要开发转向 mini-swe-agent，并推荐新使用者优先考虑后者。旧 SWE-agent 的 ACI 设计仍适合我们查阅，但不能将它描述为当前首选产品。上述更新状态依据查阅时 README；未核实每仓库最近一次提交日期，也不把 Star 数量作为方法有效性的证据。

## 对当前项目的影响

**完整函数读取、结构索引、分阶段修复和可观测轨迹都有已有工作。本项目不能以“首次实现这些能力”定位。**

求职项目的价值在于个人实现和验证：基于 CoreCoder，在本地模型与固定预算下，从失败轨迹识别证据缺失、重复阅读和上下文开销，构建有源码版本校验的阅读与候选证据链，并通过相同任务和独立评分解释策略何时有效、何时无效。这是工程与实验能力的证明；目前没有优于这些项目的证据。

我们新增的 `read_definition` 只是一个可检验干预：保持原有行数/字符上限，用 AST 找到定义边界、保留原文和文档、明确返回缺失范围，并把来源校验后的片段交给现有修复阶段。它在我们的预算设置中是否值得使用，要靠新的定位与后续修复实验回答，不能从离线完整读取就推导成功率提升。

建议阅读顺序：SWE-agent ACI → Agentless 定位流程 → aider 仓库地图 → LocAgent 图导航；mini-swe-agent 用于提醒我们，工具复杂度本身不是成果。当前不迁移整个框架；后续增加一种外部方法时，固定版本、记录许可及改动边界，并在统一评分下单独比较。
