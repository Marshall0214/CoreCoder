# 简历项目描述与面试说明

项目名称：**基于 CoreCoder 的代码修复评测与可审批 Agent 服务**。性质：个人项目 / 开源二次开发。时间按本人实际开发周期填写，技术栈只保留能够解释的部分。

## 简历可直接使用的一版

**技术栈：**Python、FastAPI、Pydantic、LangGraph、SQLite、MCP、Docker、pytest、Ollama/Qwen、BM25/Embedding。

- 优化代码修复上下文，将按行切分改为完整函数证据；在固定 Qwen、预算和独立评分的三项 Click 缺陷、各三轮对照中，验收通过次数由 **3/9 提升至 6/9**，增益集中于颜色校验任务。
- 针对一次生成补丁后仍未修复的问题，在独立实验中加入公开测试反馈与一次预算内修正，使 **usage-empty 修复由单次模式 0/3 提升至反馈模式 3/3**；最终结果由独立目标测试与回归检查共同判定。
- 将修复流程封装为可审批的 FastAPI/LangGraph 服务，使重复提交与批准复用原任务、待审批任务跨重启保留、崩溃执行标记中断且不自动重放；通过 **18 项真实 HTTP 审批故障检查**验证状态恢复与防重复执行。
- 建立独立工作区、补丁范围校验和 Trace，使修复结果、Token 与失败原因可复查；通过 MCP 将代码搜索与带哈希读取提供给外部 Client，并完成 **22 项 Docker/Linux 容器端到端检查**，验证工程链路可部署、可演示。

最后一条数字来自历史 [工程验收摘要](workflow-approval-acceptance-v1.json)。最新 Windows 全量为 **1,112 passed、2 skipped**，来自 [任务级暂存反馈摘要](tentative-feedback-v1.json)，最新任务级暂存反馈已重跑 Windows 全量，没有重跑容器或 HTTP。这些数字不是本人独立编写的测试数量，也不是修复缺陷数量；简历优先保留具体故障验收和机制。

四条贡献的代码、演示和实验出处见 [求职交付证据索引](portfolio-evidence.md)。前两条属于独立实验适配器，尚未进入默认 API 工作流。技术栈单列，正文优先写实际结果和行为变化。

面试时必须交代实验范围：3/9 与 6/9 来自三个已查看任务各三次，并非九个不同缺陷，差异集中于一个任务；第二仓库两策略均 2/3，未复现优势。公开反馈对照仅两个已知失败任务各三次，只有 usage-empty 恢复，none-salt 仍失败，反馈组总 Token 为单次组的 2.57 倍。两种实验不能合并为统一成功率，也没有整体成本下降证据。

这版能证明的提升是**特定缺陷上的修复效果，以及经过故障验收的流程可靠性**。目前不能写生产吞吐、人工耗时下降、通用修复率提升或相比成熟 Coding Agent 更优。18/22 是验收检查数量，不能解释为线上可用率。

## 60 秒项目介绍

> 我基于 CoreCoder 做了一个代码修复实验和本地服务项目。研究部分固定模型、预算和独立评分，比较代码检索与上下文组织对修复结果的影响；工程部分把同一执行器接入 API、MCP 和带人工审批的 LangGraph 工作流。每个任务都有独立工作区和验证报告，待审批状态可以跨重启保留，执行中崩溃则清理进程、避免自动重放。实验没有得出普遍提升的结论，但建立了可追溯对照、失败分析和可演示的工程闭环。

## 面试官可能追问

### 为什么做？不能直接用 Codex 或 Claude Code 吗？

> 日常开发可以用成熟工具。这个项目要解决的是我自己的机制实现和验证需求：固定同一个模型和任务预算，替换检索或上下文策略，用独立验收解释结果，再亲自实现审批、幂等和故障恢复。使用现成工具不能替代我完成这套工程与实验工作。项目的必要性是能力证明和受控实验，不是已有商业需求或产品替代。

没有做同条件产品对照，不能说更好；也不以“闭源”推导“不可控”。可控与可评估是本项目明确实现和验证的要求，并不具有独占性。

### 为什么选 CoreCoder？哪些是你做的？

> 我已经理解它的源码，核心小，方便沿用执行器并控制变量。Agent 循环、基础工具、模型客户端和原 MCP Client 来自上游；我的扩展集中在评测、证据策略实验、服务与持久化、代码知识 MCP Server、审批工作流和部署验收。用独立适配层保留冻结实验，避免服务改造悄悄改变研究协议。

路径和对应证据见 [总览的贡献表](project-overview.md)。不把上游的子 Agent、压缩或文件撤销写成个人原创。

### 实验提升了多少？

> 收益是局部的。Click 三项任务、三轮新调用中完整函数通过 6/9，行块 3/9，差异来自一个任务；第二仓库两策略都为 2/3。合成任务里 Dense 的离线召回较高，但三轮修复通过数反而低于 BM25。因此我没有替换默认策略或宣称泛化提升。

解释重复次数、评分 v2 的事前冻结，以及任务已看过、不是新的盲测。数字见 [真实仓库阶段结论](second-repo-repair-v1.md) 与 [Dense 复测](vector-repair-repeat-v1.md)。最近固定统一反馈流程的模型对照，Qwen 与 DeepSeek 均 5/6；源码契约上下文对照也均 5/6，并发生 Controls 回归，不能宣称后续策略提升了成功率。

### 最近一轮做了什么，为什么没有继续优化？

> 我先离线核查 none-salt 的必要证据，发现两个默认值已经可见，但参数转发链不完整。于是从当前源码提取带行号和哈希的 AST 事实，在同一字符预算内组织构造函数和转发片段，再固定 Qwen 做新对照。结果两组都 5/6，候选还删除了原有盐值回退，导致 Controls 失败。较少 Token 是公开执行错误停止反馈的结果，不能当作提效。模型切换和多种上下文实验均未解决它，所以冻结该方向，把已验证能力整理为可演示交付。

具体记录见 [模型对照](provider-compare-v1.md) 与 [契约上下文](source-contract-context-v1.md)。六项都是已查看任务、各一次；5/6 是该任务池的结果，不代表真实用户场景总体成功率。

### 语法检查和编辑事务为什么还会放过错误？

> 编辑器要求唯一原文匹配，事务在副本中检查编译、新增重复定义和模块加载，通过才写回。这能拒绝一部分结构错误，但模块可导入不代表所有执行分支正确。DeepSeek 曾生成不存在成员的引用，运行构造函数才报错；Qwen 的补丁也能通过加载，却破坏签名与验签的盐值关系。最终仍要看行为测试和独立 Controls，不能把事务通过当作修复成功。

离线验证拒绝 6 个历史失败补丁中的 4 个，9 个正确示例通过，见 [事务报告](patch-transaction-v1.md)。这些是已知样例验证，不是通用错误检测率。

### 独立验证为什么必要？

> Agent 说完成，或者可见测试通过，都不等于验收通过。我将候选补丁应用到干净评分副本，核对修改范围及 Target/Controls，评测材料不放进模型可读语料。验证只能证明满足这套测试，不保证完整上游行为；也曾发现评分包含公开需求之外的限制，保留旧结果并修正评分后重新冻结运行。

### 为什么需要检查点？能从任意失败节点继续吗？

> 它保存原生审批 interrupt：Worker 退出后，不占执行名额，重启后仍能批准原计划。服务先持久化不可变决定再排队，重复决定返回原任务。修复节点开始前创建独占标记；执行中崩溃后标记 interrupted，并清理进程树，不自动重放。我没有实现任意节点的断点续修，也没有保证任意副作用 exactly-once。

### MCP 和向量库做到什么程度？

> 自建 MCP Server 提供三个只读工具，已验证官方 Client 与现有 Client 互操作；服务默认检索没有自动改走 MCP。Dense 使用本地 Embedding 和内存精确余弦，Hybrid 是 RRF 排名融合，不是学习型 Reranking；向量数据库还没接入。

### 如何证明可靠性？下一步缺什么？

> 真实 HTTP 验收强制结束自己启动的服务，确认孤儿 Worker 存活，再启动新服务验证清理、中断状态及不重跑；容器里也验证待审批重启、批准和拒绝。当前证明的是本地单服务行为，未测生产负载。面向多人使用，下一步优先补身份权限、审批审计和逐任务隔离，再根据吞吐需求决定 PostgreSQL/Redis，而不是先堆组件。
