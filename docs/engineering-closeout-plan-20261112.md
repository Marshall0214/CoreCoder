# 工程收尾方案

日期：2026-11-12。状态：方案；本文件不代表接入或验收已经完成。

## 目标与边界

交付一个可从 CLI/API 运行、可演示、可复现的本地 Issue 修复服务版本。用户能提交管理员登记的任务，审批后运行新反馈流程，查看状态、候选补丁、公开验证结果与执行记录。完成下列验收后冻结本阶段。

四项已知修复失败保留为能力限制，不作为收尾阻塞。暂停修复率优化、读取接口改造、提示词实验、完整 50 项重跑、Harness² 搜索与扩权；不引入新框架、记忆系统、训练或付费 API。本方案不承诺任意仓库、任意语言或生产级服务。

## 已有基础与实际缺口

已有 CLI Issue 准备/修复入口、可信任务目录、API、幂等、SSE、取消、SQLite/LangGraph 审批恢复、Docker、Langfuse，以及旧流程的录制演示。新反馈动作循环已经过录制容器和五项本地模型验收，但尚未接入产品 CLI/API 共享入口。

本次复用现有能力，只补执行器适配及由它引起的状态、清理和报告差异。不把 `evals.feedback_pilot_v2` 的独立评分/参考答案路径搬进服务执行进程。

```text
管理员登记可信任务
        ↓
CLI / API → 审批 → 共享任务执行适配层 → 隔离工作区与新反馈循环
                                         ↓
                      状态 / 取消 / Diff / 公开测试 / 用量 / Trace
                                         ↓
                                    等待人工审查
```

真实 Issue 服务只掌握公开复现与保持检查。公开通过进入 `ready_for_review`，不表示独立验收通过或可以自动合并。基准任务的独立 Target/Controls 继续由评测器在 Agent 结束后运行。

## 一、接入同一个执行入口

- 在管理员维护的任务目录中固定可选新执行策略与参数；审批冻结其版本、输入哈希、模型、权限和实际限制。保留旧任务默认行为。
- CLI 与 `service.issues` 调用同一个任务执行适配层，不各自复制反馈流程。
- 适配层负责准备 baseline/candidate/public-checks，明确保留首轮候选生成和后续反馈阶段；无候选修改时也能将未变的候选交给公开反馈流程。
- 只提取 v2 接受的四个公开任务字段；按实际支持范围传递 Python 读写路径，不能把全部 prepared metadata 或任意文档路径直接传入。
- 复用已验收的工具、Schema、上下文策略、轮次与本地 Provider，不在接入过程中同时改修复策略。
- 录制和本地模型模式共用执行调度、工具与验证，只替换响应来源。明确处理 ScriptedProvider 的观测路径，不能套用只接受 Ollama 的适配器。

涉及：`repairflow/issue_registry.py`、`issue_repair.py`、`__main__.py`、`service/issues.py`，必要时增加独立适配模块。

完成条件：同一可信录制任务经 CLI/API 使用同一执行策略，输出相同 Diff、公开结果与协议标识；审批前零执行。

## 二、统一状态、取消和交付

复用现有任务状态，不重新建设调度或审批系统。需要处理四个实际接口差异：

1. **结果含义**：原始 v2 的 `accepted` 仅指公开验证。适配为产品的 `public_checks_passed`、`delivery_status`，产品 `accepted=false`、`independent_verification.available=false`；公开通过且有有效修改才能待审查。
2. **所有权与清理**：服务按任务根目录清理容器，v2 默认按反馈输出目录归属。显式统一可信 owner，区分路径与哈希参数；取消、超时、中断只清理本任务的进程和容器。
3. **时间配置**：服务默认 240 秒，修复阶段有 1200 秒边界。明确批准的执行配置，审批展示值与实际服务/阶段超时一致，不静默沿用旧 Token 限制或全局放宽其他任务。
4. **部分证据**：定义失败、取消、超时、中断时可下载的报告与已有补丁；未验证候选必须明确标注，不套用另一版本的通过结果。不存在的产物返回明确状态。

产物继续通过固定白名单和目录边界交付：Diff、报告、协议/来源、动作、上下文选择摘要、本地 Trace 与可用的 Langfuse 链接。幂等提交、审批恢复和拒绝审批沿用现有实现。

涉及：`service/manager.py`、`service/app.py`、共享适配层与必要的 v2 参数衔接。

完成条件：CLI/API 状态一致；运行中取消可清理所属容器并保留已有证据；服务中断的运行任务标为 interrupted，不承诺自动续跑推理或再次执行副作用。

## 三、一次有限的零模型验收

扩展已有 `repairflow.issue_demo`，使用本地冻结任务与录制响应，真实运行工具和 Docker。首次演示无需联网导入仓库、下载镜像或启动模型。

| 验收情形 | 预期 |
| --- | --- |
| 完整修正 | 公开失败 → 读取 → 错误修改 → 再验证失败 → 再定位与修改 → 公开通过；CLI/API 同 Diff |
| 审批与恢复 | 等待审批时重启后仍等待；批准后执行；拒绝则零执行 |
| 重复请求 | 同幂等键重复提交返回同一任务；重复审批不重复执行；冲突请求明确拒绝 |
| 未修好 | 达到请求上限后返回未解决及已有制品，不宣称完成 |
| 取消与超时 | 排队/运行中取消及超时状态准确，所属进程和容器清理，不影响其他服务 |
| 可观测性 | 录制响应标为 Span，真实模型调用 0，用量不伪装成实测；Langfuse 可用时回读成功，不可用时本地报告仍可交付 |

测试以改动区域回归、录制 CLI/API 集成与必要的真实 Docker 为限；每项通过即结束该项验证。演示不是模型能力实验，四个真实失败任务不在本轮重跑。

所有新目录、SQLite、临时文件和日志在 D 盘，复用已有 conda 与镜像。使用独立数据目录和可用端口，不占用现有服务目录，不自动重启 Docker/WSL。

完成条件：保存验收命令、退出码、每项结果、输入/实现哈希、零模型调用证明与产物路径。失败仅修阻塞此验收的工程缺口，不扩大研究范围。
