# 当前修复失败的已有方法与落地建议

检索日期：2026-10-07。只依据官方文档、作者论文和原始开源仓库。本轮为检索与只读环境核查，没有模型推理调用、依赖安装或实现改动。

当前证据来自 [关系矩阵对照](salt-relations-feedback-v1.md)：两组均 0/3，错误包含 None/default 语义、反馈新增重复方法，以及 `_t.str_bytes` 注解引发的模块加载错误。它们需要分别处理，不能仅归因于检索或模型能力。

## 1. 先校准推理和采样配置

[Qwen3.5-27B 官方模型卡](https://huggingface.co/Qwen/Qwen3.5-27B)推荐精确编码的 thinking 配置使用 temperature=0.6、top_p=0.95、top_k=20；这与现有 temperature=0、reasoning_effort=none 的实验条件不同。模型卡给出的通用输出长度很大，不应直接照搬到本项目的小补丁实验。

[Ollama 兼容接口](https://docs.ollama.com/api/openai-compatibility)说明 none 可请求关闭 thinking，并应通过 /api/show 查询模型的具体支持值。本机只读查询结果：Ollama 0.34.3，qwen3.5:27b 支持 thinking，values=[false,true]，default=true。现有客户端转发 reasoning_effort，故当前 none 配置请求非思考模式；仍需小型实际请求核查其响应和用量，不能把支持元数据当作请求已经生效的证明。

建议先固定温度仅比较 thinking 开关，再固定开关比较采样，避免同时改两个因素。记录有效请求参数、最终答复是否为空、finish reason、响应结构及供应商返回的用量；若 thinking 与最终输出共享长度限制，必须报告截断。保持总预算上限，不能为思考组隐性扩大总消耗。

成本：低，无需换框架。它是最值得先排查的配置差异，但没有证据证明开启 thinking 就能修好 none-salt。

## 2. 编辑事务校验：先检测，再提交或回滚

[Aider 的 lint/test 机制](https://aider.chat/docs/usage/lint-test.html)会检查修改文件并尝试修复报错；[SWE-agent 论文](https://arxiv.org/abs/2405.15793)研究编辑接口和校验反馈，包含编辑错误的拦截与恢复。值得借鉴的是机制，而非直接移植整套框架。

本项目可在临时副本应用补丁，依次执行：

- AST/编译检查：语法和结构能否解析。
- AST 定义差分：是否新增同作用域重复方法；识别合法 overload、property setter 和条件定义，避免误报既有源码。
- 少量 Ruff 正确性规则：新增未定义名称、重定义等；以原版诊断为基线，不要求旧仓库通过全部风格规则。
- 独立进程 import smoke check：是否能加载目标包，使用隔离环境、来源校验、超时和进程清理。
- 公开行为检查：是否满足需求和兼容性约束。

[Ruff F821](https://docs.astral.sh/ruff/rules/undefined-name/)用于未定义名称；不能据此声称能识别所有不存在的属性。`typing.str_bytes` 是属性错误，语法解析也不会发现，必须靠合适的类型分析或加载检查。重复方法检查同样不能只依赖一种 lint 规则。

失败时原源码不提交，返回明确失败类型。模型修正仍计入原有调用及 Token 上限，不能额外赠送无限工具重试。先对已有失败补丁离线重放，验证拦截率及人工正确补丁误拒率，再建立全新模型协议。

成本：低至中。能处理重复定义、加载失败，不能解决默认盐值语义错误。

## 3. 解题与编辑分开

[Aider architect 模式](https://aider.chat/docs/usage/modes.html)先由一个请求提出修改方案，再由 editor 请求转为具体编辑；[SWE-Edit 论文](https://arxiv.org/abs/2604.26102)与[作者代码](https://github.com/microsoft/SWE-Edit)研究 Viewer/Editor 分工及编辑模型/格式评测。

适用于模型混淆“如何修复”与“如何生成精确补丁”的情况。可以让第一阶段只确定现有函数及行为变化，第二阶段仅在已定位函数内生成编辑；避免自由追加文件里已存在的方法。完整类的方法清单可以作为结构证据，无需给出整个文件。

先做不训练的小型对照；暂不引入多 Agent 调度、GRPO 或重建训练栈。两阶段请求与反馈重试是不同协议，即使总调用数相同，也不能混入旧单次/反馈对照。

成本：中。增加协议和调用开销；如果解题阶段本身给出错误语义，editor 仍会忠实生成错误补丁。

## 4. 多候选生成加公开验证筛选

[Agentless](https://github.com/OpenAutoCoder/Agentless)采用定位、生成多个候选、结合复现和回归测试选择补丁的流程。相比反复让同一个候选自我修改，它提供了一条不同的搜索路径。

如果采用，先限定小数量候选，全部消耗共享预算，分别报告 pass@1、候选中至少一个正确的 oracle 指标及实际公开验证选择后的通过率。私有 Target/Controls 只能用于最终评分，不能参与选择，否则结果泄漏。公开测试仍可能不完备，多个补丁通过它们不代表正确。

成本：中至高。现有温度 0 下重复调用不能保证产生不同候选；先完成配置校准和候选去重，再讨论扩展。

## 推荐顺序与验收

1. 配置校准：选少量人工任务，覆盖原文编辑、重复方法、错误注解、None/default 语义；把协议应用、源码加载、行为通过三个指标分开。固定模型、提示和预算，一次只改一个配置因素。
2. 编辑事务保护：零模型调用重放既有补丁及正确示例，报告检测率、误拒率与失败分类。新增协议不改写已冻结历史结果。
3. 若语义仍失败，用同一组任务比较模型或 architect/editor 分工。只有出现可复现收益，才扩大到较广真实任务集。
4. 多候选筛选作为后续选项，当前不扩大检索变体，也不继续针对 none-salt 堆叠提示。

以上成本与适用性是针对本仓库的工程判断，不是来源项目对 CoreCoder 的性能保证。所有新结果必须独立记录，不能据开源项目的 SWE-bench 成绩推定本项目收益。
