# 新 Issue 工程闭环验收（2026-10-29）

**目标：先交付完整的本地工程版本，准确率优化后置。**本轮未运行模型、不改历史成绩。当前 MVP 支持可信配置指定的 Python 仓库，CLI 与 HTTP 都能走完“输入准备 → 审批 → 修复与沙箱验证 → 报告下载”。

## 本轮补齐

| 原缺口 | 实现与验收 |
| --- | --- |
| 依赖读取与写入共用权限 | 可选 `read_only_files` 单独声明依赖；可读取，但已有原文回执也不能写入；非法范围和元数据篡改被拒绝 |
| 新 Issue 仅有 CLI | `register-issue` 生成自包含可信目录，HTTP `issues / issue-approval-v1` 接入相同执行器 |
| 审批期间输入可能变化 | 绑定准备包、配置、脚本回答与模型设置；等待/重启后重新检查哈希 |
| 新流程没有可表达的通过状态 | 增加 `ready_for_review` 终态；公开测试通过不变成独立 `accepted=true` |
| 完整流程依赖旧评测资产 | 随附合成任务及 `demo-issue`；从新目录创建并运行，无旧数据、外网或模型依赖 |
| 最新流程缺少统一入口文档 | [新 Issue 服务与演示](issue-service.md)，包含 CLI、Swagger、审批、状态、SSE 和下载 |

复用现有 FastAPI 队列、SQLite 任务/事件、LangGraph 审批、独立 Worker、Docker 执行器和补丁/Trace 机制，没有重新搭一套服务。

## 验证结果

- 完整离线回归：**1,823 passed、20 skipped，258.87 秒**。未启用的 Docker 与条件用例在 JUnit 中保留跳过原因。
- 单独启用真实 Docker：**8 passed，83.85 秒**，含四项新 Issue API 用例及四项既有 Issue CLI 回归。
- 新 API 验证：幂等提交、审批前不执行、重启恢复审批、只读依赖、公开检查后待审查、报告/补丁/Trace 下载、SSE、重复批准不重复执行、拒绝、取消及失败回滚。
- `demo-issue` 对已注册任务和随附合成任务各完成一次验收；合成任务 CLI/API 补丁一致，重复批准不重做，拒绝后无执行。
- Ruff 与 diff 空白检查通过；本轮模型调用为零。状态、临时文件与缓存继续放在 D 盘，未停止或重启 8001 服务。

首次完整回归在收集阶段发现前一轮新增的 `evals/diagnostics/` 包标记遮蔽已有 `evals/diagnostics.py`。已删除冲突的 `__init__.py`，独立测试脚本保留原路径供历史复核，解析器测试通过 `runpy` 载入可信定义；冻结证据不改写。修复后重新完整回归得到上述数字。

最初在受限环境运行部分服务测试时，本地 ASGI/socket 启动停滞，已中止该次检查；使用允许本地进程与 socket 的环境完成最终回归及 Docker 验收。没有因此更改业务判定或放宽测试。

## 范围

`ready_for_review` 表示“任务产生候选，约定公开检查通过”，仍需人工审查。失败或中断也有明确状态，不自动重放已启动的执行。审批仅针对开始执行，下载补丁后是否提交由用户决定。

合成任务是工程验收夹具，不是真实 GitHub 缺陷，不计模型准确率。原 Click 模型失败、四项样式回归及历史 47/50 保留原结论；只读依赖功能未通过新模型运行验证是否改善 Click 修复。

这是本地单实例、指定任务、源码运行、Swagger 演示的 MVP。独立前端、通用自主搜索、多租户、分布式部署、任意仓库环境适配与自动 PR 尚未实现，准确率研究后置。
